# GST Daily Validation - Evidence Package Spec

## 1. Overview
The Daily Evidence Package is an immutable daily snapshot of business operations, tax liabilities, and inventory movements. This package serves as proof of operations for audit, GST compliance, and dispute resolution. 

## 2. Package Components
Each daily package is a compressed archive (e.g., `evidence_YYYY-MM-DD.zip`) containing the following artifacts:

### 2.1 Sales Register (`sales_register.csv`)
A complete log of all outward supplies (B2B, B2C, Exports) created, modified, or cancelled during the day.
- **Columns:** Document ID, Document Number, Date, Party GSTIN, Taxable Value, CGST, SGST, IGST, Cess, Total, Status.

### 2.2 Purchase Register (`purchase_register.csv`)
A complete log of all inward supplies received.
- **Columns:** Document ID, Document Number, Date, Supplier GSTIN, Taxable Value, CGST, SGST, IGST, Cess, RCM Applicable, Total.

### 2.3 Stock Movement Register (`stock_movement.csv`)
A log of inventory changes to reconcile physical stock with financials.
- **Columns:** Item Code, HSN Code, Opening Qty, Inward Qty, Outward Qty, Closing Qty, Valuation.

### 2.4 Tax Filings Drafts
Pre-computed daily equivalents of the GST returns, generated using the canonical representations.
- `gstr1_draft.json`: Computed GSTR-1 payload for the day's sales and outward credit/debit notes.
- `gstr3b_draft.json`: Computed GSTR-3B summary based on sales, purchases, and ITC utilization.

### 2.5 ITC Register (`itc_register.csv`)
A ledger of Input Tax Credit claimed, deferred, or reversed (e.g., Rule 37 compliance) during the day.
- **Columns:** Document Number, ITC Status, Eligible CGST, Eligible SGST, Eligible IGST, Reconciliation Status.

### 2.6 Payment Register (`payment_register.csv`)
A summary of cash and bank movements for the day.
- **Columns:** Payment ID, Date, Type (Receipt/Payment), Amount, Mode, Linked Documents.

### 2.7 Integrity Manifest (`manifest.json`)
Cryptographic hashes of all files in the package to ensure tamper-evident storage.
```json
{
  "date": "YYYY-MM-DD",
  "generated_at": "YYYY-MM-DDTHH:MM:SSZ",
  "files": {
    "sales_register.csv": "sha256_hash",
    "purchase_register.csv": "sha256_hash",
    "stock_movement.csv": "sha256_hash",
    "gstr1_draft.json": "sha256_hash",
    "gstr3b_draft.json": "sha256_hash",
    "itc_register.csv": "sha256_hash",
    "payment_register.csv": "sha256_hash"
  },
  "package_signature": "rsa_signature_or_hmac"
}
```

## 3. Generation Workflow
1. **Trigger:** A daily cron job runs at 23:59:00 local time.
2. **Extraction:** Data is fetched from the primary relational database (PostgreSQL/SQLite) and mapped into the canonical formats defined in `REPORT_DATA_CONTRACT.md`.
3. **Transformation:** The canonical objects are flattened into CSV files or nested into JSON documents as required.
4. **Hashing & Signing:** The `manifest.json` is generated by computing SHA-256 hashes for each file.
5. **Archival:** The files are compressed into a ZIP archive and uploaded to immutable storage (e.g., AWS S3 with Object Lock or a WORM drive).

## 4. Recovery and Audit
During a tax audit, the package for the requested date can be extracted. The auditor can recalculate the hashes of the CSV/JSON files and match them against the `manifest.json` to verify that records have not been retroactively altered.
